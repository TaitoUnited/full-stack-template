# CI systems

The CI configuration runs the Taito pipeline in a fixed order: build preparation, artifact preparation, database deployment, application deployment, wait, tests, verification, release tagging, and build release. The Cloud Build pipeline records those dependencies explicitly, so a database migration cannot start before the server artifact is available and deployment cannot race an unfinished artifact build. Its `E2_HIGHCPU_8` worker accommodates concurrent client, server, worker, and Playwright artifact builds; Playwright remains a dependency of testing rather than deployment so its build can overlap rollout.

Source verification and deployment serve different purposes. The GitHub PR check matrix and other source jobs should run the affected package's `npm run verify` command, or the root `npm run verify` command when verifying the complete template. `npm run verify:guidance` validates shared agent guidance, links, and skill symlinks. Deployment jobs own artifact creation, remote migrations, rollout, and remote service tests. Keep their readiness handoff explicit so an E2E job cannot test an unrelated revision or an incompletely deployed environment.

`cloudbuild.yaml` accepts an optional `_PR_NUMBER` substitution. When present, it derives the target as `pr-<number>` rather than trusting the branch name, recreates that PR's isolated database before migrations, and gives it the same pipeline dependency graph as a branch deployment. Branch builds leave `_PR_NUMBER` empty and do not recreate a database.

`cloudbuild-pr-cleanup.yaml` is intentionally separate. Configure a pull-request-close trigger to invoke it with `_PR_ACTION=closed` and the positive integer `_PR_NUMBER`; the trigger must be limited to this repository. It first cancels active builds for that PR and only then stops the `pr-<number>` deployment and drops its database. Do not add this file to a normal push trigger. See [PR environment cleanup](pr-environment-cleanup.md) for the required Cloud Build and GitHub configuration.

The repository still contains the legacy self-hosted GitHub deployment workflow. Do not enable a second active GitHub PR deployment/E2E workflow until that workflow is retired or deliberately narrowed: otherwise both providers can deploy and clean up the same PR environment.

When changing CI, preserve the distinction between artifact promotion and deployment verification. Keep secrets in the CI secret store, do not expose them in logs, and verify the exact branch/environment path affected by the change. Ensure `package.json` and its lockfile stay aligned, and run locally available package checks before handing off a pipeline change.
